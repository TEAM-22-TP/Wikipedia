    Zostručnené

    1. Charakteristika a požiadavky senzorických dát

    • Senzorické dáta sú generované v reálnom čase stovkami až tisíckami čidiel:

      - teplota,

      - vlhkosť,

      - tlak,

      - vibrácie,

      - výkon strojov,

      - spotreba energie.

    • Každé meranie obsahuje časovú pečiatku → vznikajú rozsiahle časové rady (time-series).

    • Digitálne dvojča potrebuje okamžité dáta pre vizualizáciu a simuláciu → nízka latencia je kritická.

    • Z dlhodobého hľadiska je potrebné uchovávať históriu pre:

      - analýzy,

      - reporting,

      - audit,

      - prediktívnu údržbu.

    • Architektúra musí oddeliť:

      - rýchle dáta (hot),

      - dlhodobú archiváciu (cold).

    2. Typy senzorov a dopad na výber technológie

    • Analógové senzory (0–10 V, 4–20 mA, odpor, termočlánky):

      - vyžadujú PLC s ADC,

      - generujú stabilný, častý stream,

      - vhodné pre TSDB.

    • Digitálne senzory (RS-485/Modbus, I²C, SPI, MQTT):

      - poskytujú vyššiu granularitu a kontext,

      - ideálne pre streamingové spracovanie.

    • IoT senzory cez MQTT/WiFi:

      - menšia periodicita,

      - vhodné pre broker + TSDB kombináciu.

    • Rozličné rozhrania znamenajú potrebu unifikačnej vrstvy:

      - OPC UA,

      - alebo IoT gateway.

    3. Translation Layer – preklad OPC UA dát do jednotného formátu

    • Pred odoslaním do middleware je potrebné dáta z OPC UA normalizovať:

      - vybrať iba relevantné tagy,

      - doplniť timestamp,

      - kvalitu,

      - previesť ich do jednotného formátu (najčastejšie JSON).

    • Na tento účel sú vhodné edge gateway riešenia:

      - Hopit Edge IIoT Gateway,

      - EMQX Neuron,

      ktoré umožňujú:

      - mapovanie OPC UA uzlov,

      - transformáciu dát,

      - nízkolatenčné doručovanie do MQTT / stream vrstvy.

    • Tieto gatewaye výrazne zjednodušujú integráciu, keďže digitálne dvojča pracuje už len s:

      - čistým,

      - homogenizovaným dátovým modelom,

      nie so surovou OPC UA hierarchiou.

    • Ako flexibilná alternatíva pre vývoj môže slúžiť:

      - Node-RED (s OPC UA pluginmi),

      no pre dlhodobú prevádzku sú robustnejšie dedikované edge gatewaye.

    4. Middleware – čo je vhodné pre jednotlivé scenáre

    • MQTT broker:

      - pre jednoduché IoT zariadenia,

      - nízke nároky na priepustnosť,

      - jednoduché škálovanie,

      - vhodné pre výrobnú linku s menšími dátovými tokmi.

    • Apache Kafka:

      - pre veľké objemy dát,

      - viacero konzumentov naraz,

      - replay,

      - vysoká odolnosť,

      - vhodné pre závody s tisíckami senzorov a komplexnými dátovými tokmi.

    • OPC UA:

      - vhodné tam, kde existuje PLC infraštruktúra,

      - potreba jednotného API pre čítanie údajov.

    • Cloud IoT platformy (Azure / AWS):

      - ideálne pri centralizovanom cloudovom digitálnom dvojčati,

      - vyžadujú stabilné internetové pripojenie.

    5. Porovnanie databáz – ktorý systém je vhodný pre ktorý use case

    • Relačné databázy (PostgreSQL, MySQL):

      - silné pri metaúdajoch,

      - relačných väzbách,

      - výrobnej logistike,

      - nevhodné pre vysokofrekvenčný ingest.

    • Time-Series databázy (InfluxDB, TimescaleDB):

      - optimalizované na rýchly zápis,

      - dotazy v časových rozsahoch,

      - ideálne pre senzorické dáta.

    • InfluxDB:

      - extrémne rýchly ingest,

      - jednoduchá správa retention polícií,

      - vhodné pre výrobný závod s veľkým množstvom jednorozmerných meraní.

    • TimescaleDB:

      - výhoda SQL,

      - optimalizácie pre časové rady,

      - vhodné pri kombinácii s výrobou, údržbou a ďalšími tabuľkami.

    • Apache Cassandra:

      - pre masívne objemy (miliardy záznamov mesačne),

      - geograficky distribuované závody,

      - príliš robustné pre menší enterprise závod.

    • MongoDB:

      - vhodné pre heterogénne JSON dáta,

      - nie ideálne pre primárny senzorický stream.

    6. Odporúčaný prístup pre náš use case

    (digitálne dvojča spracovne zemiakov)

    • Senzory budú generovať kontinuálne dáta:

      - teplota,

      - vlhkosť,

      - tlak,

      - hmotnosť

      → primárny dátový typ je time-series.

    • Počet senzorov je pravdepodobne stredný (desiatky až stovky):

      - Kafka nie je nevyhnutná,

      - vhodný je MQTT + prípadne OPC UA.

    • Neexistuje potreba globálnej distribúcie:

      - Cassandra by bola zbytočne komplexná.

    • Potrebná je reálna vizualizácia stavu linky:

      - TSDB s rýchlym prístupom k posledným hodnotám je ideálna.

    • Zároveň je potrebné ukladať informácie o:

      - zariadeniach,

      - linkách,

      - šaržiach

      → patrí do relačnej DB (PostgreSQL).

    • Najvhodnejšia architektúra:

      - MQTT / OPC UA → Stream → InfluxDB (senzorické dáta) + PostgreSQL (riadiace / organizačné dáta).

    7. Reálny čas vs. archivácia – čo je pre náš projekt kľúčové

    • Digitálne dvojča musí aktualizovať vizualizáciu v reálnom čase:

      - TSDB s nízkou latenciou.

    • Dlhodobé dáta slúžia na optimalizáciu výroby:

      - napr. teplota sušenia vs. kvalita produktu.

    • Retention policies:

      - sekundové dáta: 6 mesiacov,

      - agregované dáta: napr. 5 rokov.

    • Downsampling:

      - hodinové / denné priemery,

      - šetrí disk bez straty trendov.

    • Pri prediktívnej údržbe je kvalitná historická databáza nevyhnutná.

    8. Finálne odporúčanie architektúry pre fabriku na spracovanie zemiakov

    • Unifikačná vrstva:

      - OPC UA (ak sú PLC),

      - inak MQTT IoT gateway.

    • Middleware:

      - MQTT broker pre zber telemetrie,

      - možnosť rozšírenia o Kafka pri raste závodu.

    • Primárna databáza:

      - InfluxDB pre všetky senzorické dáta

      - rýchly zápis,

      - retention,

      - downsampling.

    • Sekundárna databáza:

      - PostgreSQL pre metaúdaje:

      - stroje,

      - linky,

      - šarže,

      - parametre.

    • Hot path:

      - posledné dáta pre digitálne dvojča

      - vizualizácia,

      - alarmy.

    • Cold path:

      - export historických dát do lacného uloženia:

      - Parquet,

      - S3 / Blob,

      - pre analýzy a ML.

    • Tento model:

      - minimalizuje náklady,

      - zjednodušuje správu,

      - poskytuje vysokú spoľahlivosť.

    9. Možné riešenia HMI / GUI

    Grafana + Prometheus / Influx / Timescale

    • dashboardy,

    • alerty,

    • monitoring,

    • vhodné pre KPI a historické trendy,

    • možnosť doplniť vlastné panely.

    Vlastné riešenie (Python + PyQt5)

    • nízka latencia pre realtime HMI,

    • interaktívna schéma,

    • trendy,

    • alarmy,

    • vizuálne upozornenia,

    • flexibilita deploymentu.

    • Komunikácia:

      - MQTT,

      - WebSocket,

      - REST.

    • Možnosť:

      - fallback bufferu,

      - zmeny správania pri poruche.

    • Integrácie:

      - webhooks,

      - embedding externých prvkov.

    Kombinovaný prístup

    • realtime HMI cez vlastné middleware riešenie,

    • KPI a alerty cez Grafanu.

    • Pri geospatial dátach:

      - možnosť použiť KeplerGL

      - integrovaný do frontendu alebo ako embedded panel.
